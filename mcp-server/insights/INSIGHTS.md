## What Doesn't Work

2026-08-23 — `z.preprocess(emptyStringAsUndefined, innerSchema).default(x)` does NOT treat `""` as unset: `ZodDefault` only substitutes its default when the *raw* field value is `undefined`, before the wrapped preprocess ever runs, so `""` still reaches `z.coerce.number()` and becomes `NaN`. Put `.default(x)` *inside* the preprocess's inner schema instead — `z.preprocess(emptyStringAsUndefined, z.coerce.number().int().positive().default(x))` — so the transform-to-`undefined` happens before the default check. ref: mcp-server/src/config.ts:38

2026-08-23 — A helper function that returns `z.string().optional()` in one branch and `z.string().default(x)` in another (same function signature, runtime `if`) collapses to a single static return type (`ZodOptional<ZodString> | ZodDefault<ZodString>`) for *every* call site, so callers passing a default still get an optional/`undefined`-typed field. Split into two differently-named functions (`requiredStringEnvVar` vs `optionalStringEnvVar`) instead of one function with a runtime branch. ref: mcp-server/src/config.ts:44

2026-08-23 — Same self-referential doc-comment trap as `run-review.ts`'s `JSON.stringify` case, hit again in T12 (`run-agent-on-pr.ts`): the task's own acceptance test does `readFileSync(...).not.toContain('deps.api.')` on the tool file's raw source, so writing the enforced rule into a doc comment as the literal string `` `deps.api.*` `` makes the file fail its own "thin handler" test even though the code never calls it — the substring match doesn't distinguish code from prose. Fixed by describing the constraint without spelling out `deps.api.` anywhere in the file (paraphrase as "the injected dependency bag's individual adapters"). Any tool file under a "no `deps.X.` substring" acceptance check must keep that literal token out of its own comments too. ref: mcp-server/src/tools/run-agent-on-pr.ts:12

## What Doesn't Work

2026-08-23 — `expect(tool).not.toHaveProperty('title')` on a `Tool` object returned by `client.listTools()` (`@modelcontextprotocol/sdk@1.30.0`) FAILS even though `server.ts` (T17) never passes `title` to `registerTool()` and the real wire JSON contains no top-level `title` key. The SDK client parses the JSON-RPC response through `ToolSchema` (`ZodOptional`), and Zod's `.parse()` sets every optional field as an own property with value `undefined` rather than omitting the key — so `'title' in tool` and `Object.prototype.hasOwnProperty.call(tool, 'title')` are both `true`, and Vitest's `toHaveProperty` follows suit (only `JSON.stringify` correctly drops `undefined`-valued keys, since that's JSON.stringify's own documented behavior, not Zod's). Verified by comparing three views of the same round-trip: `Object.keys(tool)` lists `title` for all 5 tools; `JSON.stringify(result)` contains `"title"` exactly once, and only inside a `Finding`'s own `outputSchema.properties.title` (the legitimate finding-title field kept per R15's carve-out), never as a top-level `Tool.title`. A future T20 assertion for "no tool carries a title key" must check `tool.title === undefined` or scan the `JSON.stringify`'d payload — never `toHaveProperty('title')` / `'title' in tool`, both of which false-positive as "has title" on this SDK version regardless of what `server.ts` registers. ref: mcp-server/src/server.ts:104

2026-08-23 (T19) — Neither of the plan's two documented `.mcp.json` command forms actually works when the subprocess is spawned with `cwd` = repo root — which is exactly what Claude Code does for a project-scope `.mcp.json`. Root cause: `tsx@4.x` resolves `tsconfig.json` (and therefore the `paths` mapping needed for `@devdigest/reviewer-core/prompt`) by walking UP from `process.cwd()` of the spawned process, not from the entry-file's own directory. `mcp-server/tsconfig.json` lives in a subdirectory of repo root, not an ancestor of it, so when cwd is the repo root (or anywhere outside `mcp-server/`), tsx never finds it and the process crashes on the very first deep import with `ERR_MODULE_NOT_FOUND: Cannot find package '@devdigest/reviewer-core'`. Reproduced for BOTH documented forms: `mcp-server/node_modules/.bin/tsx mcp-server/src/index.ts` and `npx -y tsx mcp-server/src/index.ts`, run with `cwd=/Users/alexloyko/dev-digest` (repo root) and even `cwd=/tmp` — both fail identically; only `cwd` inside `mcp-server/` (or an explicit override, see the "What Works" entry below) succeeds. `test -x mcp-server/node_modules/.bin/tsx` passing (the binary exists and is executable) says nothing about whether the *script* will run correctly from a different cwd — that check alone is not sufficient verification for T19. ref: .mcp.json:1

2026-08-23 (T21) — `Client.callTool()`'s real declared return type (`@modelcontextprotocol/sdk@1.30.0`, `client/index.d.ts:431`) is a UNION of the modern `{ content, isError?, structuredContent? }` shape and a legacy `{ toolResult: unknown }` compatibility branch that has no `content`/`structuredContent`/`isError` keys at all — only the shared `[x: string]: unknown` index signature covers those names on that branch. ## Tool & Library Notes

2026-08-23 — On the pinned `@modelcontextprotocol/sdk@1.30.0`, a genuinely empty `ZodRawShape` (`{}`, the canonical "no-params" `inputShape`) does NOT render as `{"type":"object","additionalProperties":false}` in `tools/list`, contrary to the L04 plan's "The five tools (exact contracts)" section. Traced empirically (registered a bare `McpServer` tool with `inputSchema: {}` and inspected `client.listTools()` over an `InMemoryTransport` pair): `_createRegisteredTool` calls `getZodSchemaObject({})` → `isZodRawShapeCompat({})` is `true` (zero-key objects are explicitly treated as valid raw shapes) → `objectFromShape({})` special-cases the zero-value case to `zod/v4-mini`'s `object({})` (`server/zod-compat.js:16-17`), NOT the vendored v3 `zod-to-json-schema` converter used for every *non-empty* shape. `zod/v4-mini`'s `toJSONSchema()` on that empty object produces `{"type":"object","properties":{}}` — no `additionalProperties` key at all, `false` or otherwise — whereas the v3 `zod-to-json-schema` path (any shape with ≥1 key) does default `additionalProperties: false`. Net effect: `devdigest_list_agents`'s real wire schema is `{"type":"object","properties":{}}`, not the plan's literal quoted string, even though the tool correctly accepts zero arguments either way. Matters for whoever implements T17 (`server.ts`) and T20 (`tools-list-budget.test.ts`) — T20's stated acceptance ("`list_agents.inputSchema` deep-equals `{type:'object', additionalProperties:false}` (allowing an empty `properties: {}}`)") will need updating to also allow "no `additionalProperties` key present" for this SDK version, or the assertion needs `'additionalProperties' in schema ? schema.additionalProperties === false : true` rather than a strict deep-equal. `list-agents.test.ts` asserts this defensively for the same reason. ref: mcp-server/src/tools/list-agents.ts:14

2026-08-23 — RESOLVES the Open Question below about T9's transient-retry / absent-run_id gap: both behaviors are now implemented in `wait.ts`. Two independent *consecutive* counters (`consecutiveFailures`, `consecutiveMissing`) are reset only by the event that disproves them — any successful `listRuns()` call resets the failure counter (regardless of whether the run was found), and finding `runId` in the list resets the missing counter — so a failure and a miss never compound into the same 3-strikes budget. For the error text: 3 consecutive transient failures reuse `apiUnreachable()` from `errors.ts` (an unreachable API and repeated `listRuns()` rejections are indistinguishable from this loop's vantage point, and that builder already names `./scripts/dev.sh`); for `run_id` absent from the list, no existing `errors.ts` builder fits (`unknownRunId()` implies a run this server never started at all; `noReviewForRun()` implies the run finished) — per explicit coordinator direction, this uses a minimal, factual, un-directive sentence built inline in `wait.ts` rather than inventing a new builder family, since `errors.ts` was outside this task's owned paths anyway. ref: mcp-server/src/wait.ts:120
