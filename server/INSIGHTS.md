## What Doesn't Work

- **2026-08-03** — `MockGitClient.readFile` returns `''` for an unknown path, while the real `SimpleGitClient.readFile` THROWS ENOENT. Any code that treats "the read succeeded" as "the file exists" therefore behaves differently in tests than in production — a hermetic test will report the wrong reason (a "file missing" case surfaces as "content didn't match"). Don't add a `stat`; treat empty/whitespace-only content as unresolvable, which is correct under both clients. Evidence: `server/src/adapters/mocks.ts:294`, `server/src/modules/conventions/service.ts` (`groundCandidates`).
- **2026-08-03** — A bare `confidence: z.number().min(0).max(1)` field asked of a model returns the CEILING and nothing else: across three real conventions scans it came back exactly `1.0` for all 41 candidates (`min 1, max 1, avg 1.0000`). Four fixable causes, none of them the model's fault: (1) the question was leading — it rated a rule it proposed *because* it saw consistency; (2) the prompt said "report only patterns you can SEE repeated" / "fewer, well-evidenced is better", pre-filtering output to certainties; (3) no anchors, so nothing separates 0.7 from 0.9; (4) **the score was the LAST field in the object** — JSON generates autoregressively, so it was written after an assertive rule + verbatim proof, where the top token is the max. Fix: put evidence counts (`occurrences_seen`, `counterexamples_seen`, `enforced_by_config`) BEFORE the score, give named bands, reserve `1.0` for config-enforced rules, and explicitly invite inconsistent rules. Same model, same `temperature: 0` → min 0.35 / max 0.95 / mean 0.61, 8 distinct values across 4 bands. Raising temperature is NOT the fix — that adds noise, not calibration, and breaks reproducibility. Evidence: `server/src/modules/conventions/service.ts` (`ExtractedConvention`, `SYSTEM_PROMPT`).
- **2026-08-03** — Reconcile a model's self-score against the counts it just reported, downward only: `enforced_by_config ? claimed : min(claimed, following / (following + counterexamples))`. It keeps the model as the scorer while stopping it contradicting its own evidence (claiming 1.0 while admitting 3 counterexamples), and never raises a score, so a harsh self-rating survives. Config-enforced rules are exempt — a lint rule holds repo-wide even when the sampled files show exceptions. Evidence: `server/src/modules/conventions/verify.ts` (`consistencyScore`).
- **2026-08-03** — NEVER derive a user-facing URL from a clone's git remote. `SimpleGitClient.clone` writes the authenticated URL into `.git/config`, so `git remote get-url origin` inside `<cloneDir>/<owner>/<repo>` returns `https://x-access-token:github_pat_…@github.com/<owner>/<repo>` — putting that in an `href` would publish the PAT into the DOM (and into any copied link). Build GitHub URLs from `repos.full_name` only; that is what `githubBlobUrl`/`githubPrUrl` already expect. Evidence: `server/src/adapters/git/simple-git.ts:55-68`, `client/src/lib/github-urls.ts`.
- **2026-08-03** — NEVER display `IndexState.filesIndexed` as "N files in this repo". It is a CUMULATIVE parse counter, not a file count: `pipeline/incremental.ts:257` writes `state.filesIndexed + filesIndexed`, so a file touched by three refreshes is counted three times and the total can exceed the repo's real size. It is also files PARSED, not files walked — parse failures and unsupported-lang files are excluded (they land in `filesSkipped`) yet still get a `file_rank` row. On a freshly-indexed repo the two happen to agree, which is exactly how this bug hides. The honest "how many files does this repo have for ranking purposes" is `COUNT(*) FROM file_rank WHERE repo_id = ?` — literally the candidate set `getRankedPaths` orders — exposed as `repoIntel.countRankedFiles()`. Evidence: `server/src/modules/repo-intel/pipeline/incremental.ts:257`, `pipeline/full.ts:191,229`, `server/src/modules/repo-intel/service.ts` (`countRankedFiles`).
- **2026-08-03** — NEVER pass a model-supplied path to `container.git.readFile` unguarded: it does a bare `join(clonePath, path)` with no containment check, so an `evidence_path` of `../../../../etc/passwd` escapes the clone and its contents end up rendered in the UI. Guard in two layers — a pure `isSafeRepoPath` (rejects `..` segments, posix/windows absolutes, NUL) plus a `resolve()` prefix check against the clone root — and cap how many such reads one response can trigger. Evidence: `server/src/adapters/git/simple-git.ts:129`, `server/src/modules/conventions/verify.ts`.

## Codebase Patterns

- **2026-06-18** — `POST /skills/import` must be registered BEFORE `GET /skills/:id` in Fastify routes, otherwise Fastify matches the literal segment `import` as a UUID param and returns 422. Fixed by registering the static path first. Evidence: `server/src/modules/skills/routes.ts:60`.
- **2026-06-18** — Skills wiring in reviews: `run-executor.ts` fetches `agentsRepo.linkedSkills(agent.id)`, filters to `.skill.enabled`, and passes the bodies as `{ skills: skillBodies }` to `reviewPullRequest()`. `assemblePrompt` in reviewer-core renders `## Skills / rules` automatically when the array is non-empty — no reviewer-core changes needed. Evidence: `server/src/modules/reviews/run-executor.ts`.

- **2026-08-03** — A feature that MINTS a skill needs no endpoint of its own: `POST /skills` already accepts `name`/`description`/`type`/`source`/`body`/`enabled`, and `SkillsService.create` forwards `source`, so `type:'convention'` + `source:'extracted'` work today. Build a *draft* endpoint and let the client save through `POST /skills`. The one field that does NOT reach the DB is `evidence_files` — the repository persists it but the route/service never forward it — and nothing anywhere reads it beyond `toSkillDto`, so it is dead weight, not a gap worth plumbing. Evidence: `server/src/modules/skills/routes.ts:15`, `service.ts:68`, `helpers.ts:19`, `repository.ts:21`.
- **2026-08-03** — Routes in this codebase declare `params`/`body` schemas but NOT response schemas, so a module may return a SUPERSET of a vendored contract without touching `vendor/shared/` (which is do-not-touch and hand-synced in two copies). The conventions module adds `category` / `evidence_start_line` / `evidence_end_line` on top of `ConventionCandidate` by mapping rows in its own `helpers.ts` — no contract edit, no lock-step client sync. Evidence: `server/src/modules/conventions/helpers.ts`, `server/src/modules/skills/routes.ts`.
- **2026-06-14** — Shared contracts (`@devdigest/shared`) are vendored as TWO hand-maintained copies — `server/src/vendor/shared/` and `client/src/vendor/shared/` — resolved by tsconfig path alias, NOT auto-synced. Adding a field means editing both in lock-step; the only diffs between copies are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts`, `platform.ts`.
- **2026-06-14** — PR-list per-PR aggregates (score, cost) are computed ON READ in `GET /repos/:id/pulls` via one `inArray` query + JS grouping, never denormalized onto `pull_requests`. "Latest review batch" cost has no batch id in the schema — approximated by summing `agent_runs.cost_usd` within a 120s window of the PR's newest priced run. Evidence: `server/src/modules/pulls/routes.ts`.
- **2026-06-14** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`repository/run.repo.ts`) AND the interface wrapper (`repository.ts:151`). Adding a field (e.g. `costUsd`) needs both or typecheck fails.
- **2026-06-17** — PR-list `GET /repos/:id/pulls` returns the latest batch's FINDINGS as full `Finding[]` records (not counts) under `PrMeta.findings`, mapped via `reviews/helpers.ts#findingRowToDto`; the client derives severity chips AND renders a hover popover from that one array (no second fetch, perfect chip↔popover consistency). The "latest review batch" here is a SEPARATE window from the cost block: cost windows over `agent_runs.ranAt`, findings windows over `reviews.createdAt` (both 120s). A pre-existing `rollupSeverities` helper in `modules/pulls/status.ts` (lowercase keys) was built for a counts-only variant — currently unused by the route. Evidence: `server/src/modules/pulls/routes.ts`.

## Tool & Library Notes

- **2026-08-03** — `repoIntel.getConventionSamples(repoId, n)` returns file PATHS only (it is a one-line pass-through to `getTopFilesByRank`) — reading the contents is the caller's job, via `container.git.readFile`. It returns `[]` whenever the repo is unindexed or `REPO_INTEL_ENABLED=false`, so a caller must handle "no samples" as a normal outcome, not an error. Note it also filters OUT configs (`isJunkPath` drops `eslint`/`prettier`/`.config.`), so config sampling has to be done separately — and root-only config discovery finds nothing in this multi-package repo (no root `tsconfig.json`/eslint config), which is why a real scan here sampled 12 files, all code. Evidence: `server/src/modules/repo-intel/service.ts:630,713`, `server/src/modules/conventions/samples.ts`.
- **2026-06-14** — New DB columns: edit `db/schema/*.ts`, then `npm run db:generate` (drizzle-kit) auto-generates `00NN_*.sql` (e.g. `0010_solid_baron_zemo.sql` = `ALTER TABLE … ADD COLUMN`). Never hand-write migration SQL; apply with `npm run db:migrate`.
- **2026-08-02** — `pnpm db:migrate` applies only journal entries whose `when` is NEWER than the newest `created_at` in `drizzle.__drizzle_migrations` — it does NOT diff by hash or tag. Working on several lesson branches against ONE local Postgres therefore silently skips migrations: a branch migrated at a later wall-clock date raises the DB head above a sibling branch's older `when`, and that branch's migrations never run — `db:migrate` still prints "✓ migrations applied". Symptom is a missing column at runtime, not a migration error. Diagnose by comparing `meta/_journal.json` `when` values against `select created_at from drizzle.__drizzle_migrations`; fix by applying the skipped `00NN_*.sql` by hand (they are additive `ALTER … ADD COLUMN`) or `docker compose down -v` for a clean rebuild (drops all local data). Evidence: `server/src/db/migrations/meta/_journal.json`, `0011_far_stryfe.sql`.

## Recurring Errors & Fixes

- **2026-06-14** — Adding a required field to a Zod contract (`RunStats.cost_usd`) breaks the inline fixture in `server/test/contracts.test.ts` (RunTrace parse). Update the `stats: {…}` fixture in the same change. Evidence: `server/test/contracts.test.ts:160`.
- **2026-08-02** — `ERR_MODULE_NOT_FOUND: Cannot find package 'fflate'` on `pnpm dev` after switching branches: `scripts/dev.sh` installs deps ONLY when `node_modules` is absent (`install_if_needed`), so a branch that adds a dependency starts with a stale tree and the API dies while the client still comes up fine on :3000 — easy to misread as "the stack started". Fix: `cd server && pnpm install`. Note the L02 commit added `fflate` to `server/package.json` without updating `server/pnpm-lock.yaml`, so the install rewrites the lockfile. Evidence: `scripts/dev.sh`, `server/src/modules/skills/service.ts`.
