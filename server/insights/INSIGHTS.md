## What Works

2026-06-20 — `ContainerOverrides` is the correct test-double injection point for all adapters — pass mocks via `new Container(config, db, { llm: { openai: new MockLLMProvider() }, github: new MockGitHubClient() })`. Using `vi.mock()` on an adapter module file is a code smell here: if you need it, the dependency should be constructor-injected instead. ref: server/src/adapters/mocks.ts:1

2026-06-22 — New adapter port pattern: (1) add interface to `adapters.ts` additive-only, (2) create concrete in `adapters/<category>/<name>.ts`, (3) import concrete ONLY in `container.ts`, (4) add private `_field` + lazy getter mirroring the `git` getter, (5) add `field?` slot to `ContainerOverrides`, (6) add `MockXClient` to `mocks.ts`. All six steps form one atomic unit — partial completion causes typecheck failures. ref: server/src/adapters/http/web-fetch.ts:1

2026-06-18 — Unit-testing a drizzle repo function with two sequential queries: mock `db.select()` with a call counter; each call returns a fresh chain where `.orderBy()` (first query) or `.groupBy()` (second query) resolves with the appropriate fixture data. All intermediate chain methods (`from`, `leftJoin`, `innerJoin`, `where`) return `this`. Pattern validated for `listRunsForPull`. ref: server/src/modules/reviews/repository/run.repo.severity.test.ts:53

## What Doesn't Work

2026-06-22 — Refactoring an inline SSRF guard into a container-wired adapter: the old inline helper (`safeFetchSkillUrl` in skills/routes.ts) had identical logic but was unreachable from other modules. Lifting it to `WebFetchAdapter` + `WebFetchClient` port lets the intent module reuse it via `container.webFetch.fetch()` without re-implementing SSRF guards. The route refactor must remove the unused import (`ValidationError`) or typecheck warns. ref: server/src/modules/skills/routes.ts:1

2026-06-22 — The Edit tool's `old_string`/`new_string` params silently substitute Unicode typographic quotes (curly `'`/`'`) for ASCII single-quote delimiters when the replacement block contains other Unicode characters (e.g. `·` middle-dot, curly apostrophe `'`). In `platform.ts` this produced TS1127 "Invalid character" errors across the entire `FEATURE_MODELS` array. Fix: use a Python byte-level `open(..., 'rb')`/`write` to replace only the target bytes without touching surrounding quote characters. ref: server/src/vendor/shared/contracts/platform.ts:51

2026-06-17 — `selectDistinctOn([agentRuns.prId])` for cost silently returns null when the most recent run errored (`cost_usd = null`). DISTINCT ON picks the newest row regardless of whether the value is null — so a trailing error run zeros out the entire COST column. Fix: use `sql\`sum(${t.agentRuns.costUsd})\`` with `.groupBy(t.agentRuns.prId)` — SQL SUM skips nulls, so error runs don't affect the total. ref: server/src/modules/pulls/routes.ts:122

2026-08-28 — `platform.ts` had a pre-existing `contracts-in-sync` divergence unrelated to any in-flight task: the client copy still had `review_intent` `defaultProvider`/`defaultModel` = `openai`/`gpt-4.1` with a curly apostrophe in the description, while the server copy had already been flipped to `openrouter`/`deepseek/deepseek-v4-flash` with an ASCII-safe double-quoted string. Root cause: a prior session (2026-06-22 T2 note, line 88 below) updated `client/src/lib/utils/featureModels.ts` but never touched the vendored `client/src/vendor/shared/contracts/platform.ts` copy. Since `arch-check`'s `contracts-in-sync` rule is file-scoped, any task that owns `platform.ts` end-to-end must reconcile ALL drift in that file, not just its own additions, or the rule stays red. ref: server/src/vendor/shared/contracts/platform.ts:54

2026-08-28 — T13 follow-up (project-context plan, AC-18): seed.ts first tried `!seedReview.runId` (the seeded review's `run_id` column being null) as the "have I already seeded this run+trace?" guard. Wrong on the actual shared dev DB: that review row's `run_id` was already non-null from unrelated historical data (a real run from weeks earlier, findings_count mismatched with the review's actual findings — evidence it was stale/unrelated), so the guard evaluated false and silently skipped creating the new `agent_runs`/`run_traces` rows entirely, no error. `reviews.run_id` is not a safe idempotency key for seed-created data on a long-lived, actively-used dev database — it can already be set by something seed.ts didn't create. Fixed by keying off a value only this fixture could produce: `run_traces.trace->>'specs_commit_sha'` equal to the fixture repo's commit sha (deterministic, stable across seed runs), via `sql\`${t.runTraces.trace} ->> 'specs_commit_sha' = ${fixtureCommitSha}\``. General lesson: on a DB that isn't fresh, "is column X null" is not a safe re-run guard for any column another writer (past manual testing, an older seed version, real usage) could plausibly have already touched — prefer a value that could only exist if THIS code path created it. ref: server/src/db/seed.ts:733

## Codebase Patterns

2026-06-29 — A new module's service must NOT do direct Drizzle queries (`container.db.select()`) — all DB access belongs in a dedicated `repository.ts`. This is an Onion Architecture enforcement: Application layer (service.ts) must not depend on Infrastructure (Drizzle). Pattern: `this.repo = new BlastRepository(container.db)` in the service constructor; all `db.*` calls live in `repository.ts`. Architecture reviewer catches this as a HIGH violation. ref: server/src/modules/blast/service.ts:1

2026-06-29 — Two parallel type hierarchies exist for blast radius data: `server/src/modules/repo-intel/types.ts` has internal types (`BlastChangedSymbol`, `BlastCallerRow`, `BlastResult`) used within repo-intel; `server/src/vendor/shared/contracts/brief.ts` has the HTTP contract types (`BlastChangedSymbol`, `BlastCallerRow`, `BlastRadiusResult`). They are structurally compatible but distinct — the `Blast` prefix on the shared types avoids collision. `BlastService` maps internal → contract before returning. Never merge them; the internal types can evolve independently of the HTTP contract. ref: server/src/vendor/shared/contracts/brief.ts:155

2026-06-29 — MCP tools that hit the API must be registered with the HTTP client injected: `registerGetBlastRadius(server, client, { resolvePullId })`, not `registerGetBlastRadius(server)`. A tool registered without `client`/deps can only be a stub — the moment it needs to call the API it has nothing to call. Our composition root (`mcp-server/src/index.ts`) wires `client` + application-core deps into every non-trivial tool. ref: mcp-server/src/index.ts:63

2026-06-22 — The minimal `Logger` type (`{ info, warn, error, debug }`) for new server modules is NOT exported from `@devdigest/shared` — it lives in `server/src/modules/reviews/run-executor.ts` as `export type Logger`. Import it with `import type { Logger } from '../reviews/run-executor.js'`. ref: server/src/modules/reviews/run-executor.ts:31

2026-06-20 — Layer mapping for Onion Architecture: Domain=`src/vendor/shared/contracts/` (pure TS types, zero framework imports), Application=`modules/*/service.ts` (orchestration, no SQL), Infrastructure=`modules/*/repository.ts` + `src/adapters/` (Drizzle, Octokit, OpenAI SDK), Presentation=`modules/*/routes.ts` (Fastify handlers). Documented in `.claude/skills/onion-architecture/`. ref: server/src/platform/container.ts:1

2026-06-20 — `src/platform/` is NOT an architectural layer — it is cross-cutting infrastructure (Container, RunBus, JobRunner, AppError, AppConfig) that any layer may import without violating the inward-only dependency rule. Treating it as a layer and avoiding imports from it is a mistake. ref: server/src/platform/container.ts:1

2026-08-29 — T8 (pr-why-risk-brief plan): when a task brief names an input signal (here, `BriefInputParts.blastSummary`) but gives no repository method or port for it, prefer a direct `container.<facade>` call over reusing another module's *Service* class, even when that Service already computes exactly the thing you need. `BlastService.getForPr()` (blast module) already produces a one-sentence blast summary, but calling it from `BriefService` would (a) make `service.ts` depend on a sibling module's application layer instead of a shared repository/adapter — the same class of violation `container.reviewRepo`/`container.reposRepo` getters exist to avoid — and (b) silently add a second, unaccounted `llm.complete()` call per brief generation, undermining the plan's claim that the rate-limit + single-flight guard are the *only* two spend controls on `POST /pulls/:id/brief/generate`. Resolution used instead: call `container.repoIntel.getBlastRadius(repoId, changedPaths)` directly (already a `Container` getter, zero `container.ts` changes) and compose a deterministic, non-LLM summary string from the returned counts. `RepoIntelService.getBlastRadius` already degrades to `{degraded:true, reason:'no_data'}` without throwing when the repo has no `clonePath` (`repo-intel/service.ts`'s early `if (!repo || !repo.clonePath || changedFiles.length === 0) return empty`), so this is safe to call in a plain seeded-row integration test with no real git clone — `blastSummary` just comes back `null`. ref: server/src/modules/brief/service.ts:1

2026-06-20 — Cross-module data access: a service must never import another module's `repository.ts` directly. Instead, shared repositories are pre-built as properties on `Container` (e.g. `container.agentsRepo`). To add cross-module data access, add a property to `Container` first, then use it via `this.container.X`. ref: server/src/platform/container.ts:1

2026-08-28 — `buildProjectContextSpecs` (run-executor.ts) re-checks TWO things at read time that were already checked at attach time: the scanner's `excludedReason` (via a fresh `listDocuments` lookup) and path containment (via `resolveContained`). This is deliberate, not redundant — a document safe when attached can become excluded by a LATER rescan (oversize, unreadable) or have its containment invalidated by a re-clone/symlink plant, and `service.ts`'s `validateContextPaths` only runs once, at attach time. Landed as the EC-4 fix in commit `6ac584f`, after the initial T12 implementation only checked containment, not `excludedReason`, at read time. ref: server/src/modules/reviews/run-executor.ts:705-746

2026-08-28 — `scanner.ts`'s context-root walk is NOT anchored to the repo root — a directory named `specs`/`docs`/`insights` at ANY depth starts a matched subtree (confirmed with the user as the correct reading of the spec's glob). When one context-root name nests inside another (e.g. `docs/specs/x.md`), the walker's `activeRoot` propagation makes the OUTERMOST match win — `root` on the resulting record is the outer directory's name, not the inner one. This was an open question the implementer (T8) resolved unilaterally and documented in a code comment rather than leaving ambiguous; no spec AC covers the nested case explicitly. ref: server/src/modules/context/scanner.ts:190-198

2026-08-28 — This rule has a real exception when a task's `Owned paths` excludes BOTH `platform/container.ts` (the only place a new `reposRepo` getter could be added) AND the target module's own `repository.ts` (which would need to grow a repo-lookup method). T10 (project-context plan) hit exactly this: `ContextService` needs repo metadata (owner/name/clonePath) but owned only `service.ts`/`routes.ts`/`index.ts`/`modules/index.ts`. Resolution: construct `new RepoRepository(container.db)` directly inside the service (same shape `BlastService` already uses for its *own* repository) — this keeps raw SQL out of the service file (still lives inside `RepoRepository`, an infrastructure-layer class) even though it imports a sibling module's `repository.ts`. `arch-check --no-contracts` reports zero violations for this pattern. Treat "own the service, not the container or the sibling repo" as license to construct the sibling repository class directly, not license to inline `container.db.select()`. ref: server/src/modules/context/service.ts:1

2026-06-20 — `getContext(container, req)` is the mandatory first call in every Fastify route handler — it extracts `workspaceId` + `userId` from the auth context. Never read `workspaceId` from `req.headers` manually in a handler; always go through `getContext`. ref: server/src/modules/_shared/context.ts:1

2026-06-18 — `agent_runs` stores only total `findingsCount` and `blockers` — no per-severity breakdown. To get critical/warning/suggestion counts per run, use: `findings` JOIN `reviews` (on `reviews.id = findings.reviewId`), filter `inArray(t.reviews.runId, runIds)`, group by `(reviews.runId, findings.severity)`. Second query pattern, merge into result map. ref: server/src/modules/reviews/repository/run.repo.ts:51

2026-06-17 — `nullish()` (not `nullable()` or `optional()`) is the convention for optional DTO fields in `platform.ts`. Use `z.number().nullish()` for fields that may be absent from older DB rows — accepts both `null` and `undefined` from Drizzle. ref: server/src/vendor/shared/contracts/platform.ts:157

2026-08-28 — A "barrier" task that widens a shared contract's field type (e.g. `RunTrace.specs_read: string[] → SpecRead[]`) cannot itself make `pnpm typecheck` green across every consumer package if the plan also forbids it from touching the consumer files (they're owned by dependent tasks that run after the barrier lands). Confirmed for the `specs_read` widening: it breaks `server/src/platform/trace-builder.ts:52` (`specs_read: input.specsRead` where the input type is still `string[]`) and `client/.../RunTraceDrawer/_components/TraceBody/TraceBody.tsx:45` (renders a `SpecRead` object directly as `ReactNode`) — both explicitly out of scope for the contract-owning task. Diffed against the pre-change baseline to confirm these are the ONLY new errors (server's 9-error `run.repo.severity.test.ts` baseline is unchanged). Treat "own the contract, don't touch the consumer" plus "typecheck must stay green" as a real tension to flag, not silently work around by touching an out-of-scope file. ref: server/src/platform/trace-builder.ts:52

2026-08-28 — `seed.ts`'s exported `seed(db, cloneDir?)` takes an optional second parameter defaulting to a `defaultCloneDir()` helper that replicates `platform/config.ts:77-79`'s `DEVDIGEST_CLONE_DIR`-or-`~/.devdigest/workspace` logic inline, rather than importing `loadConfig` — keeps every existing `*.it.test.ts` caller's `seed(db)` call working unchanged while still letting a caller override the clone dir. seed.ts is on `scripts/arch-check.sh`'s `no-process-env-outside-allowlist` allowlist, so reading `DEVDIGEST_CLONE_DIR` there directly is not a violation. ref: server/src/db/seed.ts:34

2026-08-28 — `repos.list()` (`RepoRepository.list`) has no `ORDER BY`, so Postgres returns rows in roughly insertion order for a freshly seeded table with no updates/vacuum. e2e flows that follow the home redirect to "the first repo" depend on this: `seed.ts` inserts the demo repo with real fixture content (`acme/payments-api`) strictly before the clone-less demo repo (`acme/docs-portal`), so the redirect lands on the repo with content. Do not reorder those two inserts, and do not assume this ordering holds on a long-lived dev DB with rows from outside seed.ts (verified one had a pre-existing manually-added repo row that predated and outranked both seeded rows). ref: server/src/modules/repos/repository.ts:32

2026-08-28 — T12 (project-context plan): `buildEffectiveSet` (ordering.ts, owned by T4) dedupes duplicate paths silently — it returns only the kept set, never the dropped ones — but the plan requires every ATTACHED document (including ones dropped as duplicates) to appear in the trace. Rather than editing `ordering.ts` (out of scope), the executor recovers the dropped set itself: build `effectivePaths = new Set(effectiveSet.map(d => d.path))`, then walk `[...agentDocs, ...skillDocs]` (agent docs listed first, matching `buildEffectiveSet`'s own agent-beats-skill priority) with a `claimed` Set — the FIRST raw occurrence of a path that is in `effectivePaths` is the one `buildEffectiveSet` kept; every other occurrence (later duplicate in the same list, or any skill copy after the agent copy already claimed it) becomes a `status: 'duplicate'` `SpecRead`. This only works because agent-docs-before-skill-docs concatenation order already matches `buildEffectiveSet`'s cross-group priority — it does NOT reproduce `ordering.ts`'s within-group sort (`position` / `skillOrder`), which turned out not to matter for correctness since same-path duplicates are the identical document regardless of which specific row is "kept". ref: server/src/modules/reviews/run-executor.ts:1

2026-08-28 — T12 (project-context plan): the executor has the run's ACTUAL repo (`repo: typeof schema.repos.$inferSelect`, passed into `runOneAgent` already) — deliberately did NOT reuse `ContextService`'s `resolveRepoForWorkspace` "first repo with a clone" heuristic (see the T11 entry above) for reading spec files, since that heuristic exists only because `ContextService`'s routes have no `:repoId`. `container.git.readFile({owner, name}, path)` internally recomputes the clone path via `SimpleGitClient.clonePathFor` (`join(cloneDir, owner, name)`), which is guaranteed to equal `repo.clonePath` for the correct run repo — so passing `{owner: repo.owner, name: repo.name}` from the run's own repo row is both correct and simpler than threading `repo.clonePath` through as a raw fs path. `container.git.currentHead()` takes the same `RepoRef` shape (`currentHead(repo: RepoRef)`, NOT zero-arg) despite what a plan's prose may say — confirmed against `adapters/git/simple-git.ts:90` before using it. ref: server/src/modules/reviews/run-executor.ts:1

2026-08-29 — T9 (pr-why-risk-brief plan): distinguishing `model_error` from `invalid_result` for a THROWN error out of `llm.completeStructured` is done by testing the error message for the substring "schema" — both `MockLLMProvider` (`adapters/mocks.ts:95-97`, throws `"MockLLMProvider fixture failed schema: ..."`) and the real adapters (`adapters/llm/openai.ts`, `anthropic.ts`, which throw `ExternalServiceError("... failed schema validation")` after exhausting retries) use that wording, so it's a reliable, adapter-agnostic signal rather than mock-specific special-casing. Separately: `completeStructured`'s generic `StructuredResult<T>` return type is a compile-time label only — every current implementation (mock included) already validates internally before ever returning, but the service still re-runs `PrBrief.safeParse(result.data)` at the boundary rather than trusting `T`, per the zod "parse, don't trust boundaries" rule — this is also what makes an out-of-set `risk_level` a caught validation failure even for a hypothetical adapter that returns instead of throwing (EC-10). ref: server/src/modules/brief/service.ts:37

## Tool & Library Notes

2026-06-17 — `sql` template tag from `drizzle-orm` is NOT included in the common named-export bundle used in this file (`and, desc, eq, inArray`). When adding raw SQL expressions (e.g. `sql\`sum(...)\``), add `sql` to the import explicitly: `import { and, desc, eq, inArray, sql } from 'drizzle-orm'`. Missing it gives a "sql is not defined" runtime error, not a TS error. ref: server/src/modules/pulls/routes.ts:3

2026-06-17 — Drizzle `selectDistinctOn([col])` requires the first `orderBy()` column to match the DISTINCT ON column. For "latest row per group": `.selectDistinctOn([t.agentRuns.prId], {...}).orderBy(t.agentRuns.prId, desc(t.agentRuns.ranAt))`. Without the matching prId in orderBy, Postgres throws "SELECT DISTINCT ON expressions must match initial ORDER BY expressions". ref: server/src/modules/pulls/routes.ts:1
